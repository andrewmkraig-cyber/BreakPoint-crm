# Candidate lists — schema (5A.4.a)

Lists are stored in two new Neon tables: `CandidateList` (one row per list, with `organizationId` for tenant scoping, a unique `(organizationId, name)` constraint, and a `createdById` attribution) and `CandidateListMembership` (one row per candidate-on-list, joining `listId` and `candidateId` with `(listId, candidateId)` uniqueness so the same candidate can't be double-added). Both tables ride the existing org boundary: deleting an organization cascades through its lists; deleting a list cascades through its memberships (but leaves candidates untouched); deleting a candidate cascades through their memberships (but leaves the lists untouched). No UI ships with this migration — list management lands in 5A.4.b on top of this foundation. Migration applied via `npx prisma db push` against the shared Neon DB (the project doesn't use `prisma/migrations/` files; schema state is the canonical migration history).
